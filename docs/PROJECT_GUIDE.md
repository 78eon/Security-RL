---

## 1. What it does

When a security team wants to know how an attacker could break into their network, someone has
to work it out by hand: which machine is exposed, what runs on it, where you can get to from
there. It is slow and depends on the expertise of whoever is doing it.

**RLRedTeam trains a computer program to work that out by itself.** The program is dropped into
a simulated network it has never seen, knowing almost nothing about it. It has to scan, discover
machines, break into them, and escalate access until it reaches the machines that matter. It is
not told how — it learns by trying, failing, and being scored. That scoring method is
*reinforcement learning*, the same family of technique used to train game-playing agents.

The research question is about **what we score it on**. The obvious approach is to reward it only
for reaching the target. This project instead rewards it in proportion to **how severe the
real-world vulnerabilities are** that it exploits along the way, using published severity scores
from the US National Vulnerability Database. The experiment tests whether that extra information
makes the agent learn faster, and whether it changes *which* path it finds.

> **One-sentence version.** It trains an AI to discover attack paths through randomly generated
> networks, and tests whether feeding it real vulnerability-severity data helps it learn faster
> than a plain reward that only says "you reached the target".

**Nothing here touches a real network.** Every network is synthetic, generated by an open-source
academic simulator (NASim). No live systems are scanned, no real machines attacked, no people
involved. The vulnerability data is public reference material — severity scores and descriptions
— not exploit code. The trained agent's weights are kept out of the public repository by default,
because an attack-path-finding model is dual-use.

## 2. How it fits together

Five stages, each handing output to the next.

| # | Stage | In plain terms | Files |
|---|-------|----------------|-------|
| 1 | Collect vulnerability data | Download real records from NVD and freeze them locally, so the experiment gives the same answer next month as today | `tools/fetch_nvd.py`, `catalogue.py`, `manifest.py` |
| 2 | Build a random network | Generate machines, services and firewall rules from a seed — random but repeatable | `topology.py` |
| 3 | Attach vulnerabilities | Give each way-in a real vulnerability, spread across the severity range | `assign.py` |
| 4 | Score every move | Look up how severe the vulnerability used was, turn it into a number | `events.py`, `cvss.py`, `reward.py`, `nasim_adapter.py` |
| 5 | Train and record | Run the learning algorithm; write every episode to a database | `train.py`, `storage/postgres_logger.py` |

**Why it is built in this order.** The scoring engine *deliberately* knows nothing about the
network simulator — it cannot even import it. It scores a plain description of "what just
happened". That meant the whole scoring system could be tested before the simulator was
connected, and if the project ever swapped simulators, only one file would need rewriting.

## 3. The four key ideas

### 3.1 Severity becomes reward

Every vulnerability has a published severity score from 0 to 10 (CVSS). The system converts that
into reward points — but on a curve, not a straight line.

| CVSS | Severity | Weight | Reward points |
|-----:|----------|-------:|--------------:|
| 3.7 | LOW | 0.353 | 0.88 |
| 5.3 | MEDIUM | 0.461 | 1.15 |
| 7.8 | HIGH | 0.706 | 1.77 |
| 9.8 | CRITICAL | 0.970 | 2.43 |
| 10.0 | CRITICAL | 1.000 | 2.50 |

**Why curved?** Real vulnerabilities that let you break in remotely are nearly all scored 7.8 to
10.0 — they cluster at the top. On a straight line the most severe would be worth only about
1.4× the least severe, smaller than the natural variation between training runs, so the effect
would be invisible. The curve widens the spread to **2.84×**, large enough to detect.

### 3.2 Two agents, identical except for the reward

The **shaped** agent gets the severity-based reward. The **sparse** agent gets one point for
reaching the target and nothing else. Everything else — network, vulnerabilities, seeds,
algorithm — is held identical and verified by checksum before training starts. That is what makes
this a fair test rather than an anecdote.

### 3.3 Stopping the agent cheating

An early version of the reward would have been catastrophically exploitable. The agent earns a
point for scanning; scans always succeed and can be repeated. Over a 1,000-move episode it could
have earned **+1,000 points by scanning the same machine repeatedly**, against +100 for actually
reaching the target. The optimal strategy would have been to scan forever and never attack.

The fix: a reward pays only the *first* time an action reveals something genuinely new, and
breaking into a machine pays only when access level actually rises. A check at startup refuses to
train if the settings would let cheating win.

### 3.4 Random networks, not one fixed network

Discovered by testing: on the simulator's standard example network, **7 of 8 machines could only
be attacked one way**. The agent had no choice to make, so severity was a constant — and
constants cannot influence a decision. The experiment would have measured nothing.

Generated networks are configured with more attack methods than services, giving roughly four
applicable options per machine — a real decision, on every seed tested.

## 4. What every file does

### The scoring engine — knows nothing about networks

No dependency on the simulator; testable on its own.

| File | Lines | In plain terms |
|------|------:|----------------|

| `storage/postgres_logger.py` | 286 | Writes episodes in batches; survives a failed write |
| `storage/schema.sql` | — | Three tables: experiments, episodes, steps |

### Scripts run by hand

| File | Lines | In plain terms |
|------|------:|----------------|
| `scripts/rollout_random.py` | 142 | A completely random agent — the baseline to beat, and proof the simulator works |
| `scripts/run_ablation.py` | 127 | Lists the experiment grid and proves both arms are comparable before spending compute |

### The tests — 156 of them

Roughly 1,000 lines of tests against 2,000 lines of code. Worth naming in a meeting:

- **The cheating test** — scans one machine 1,000 times, checks the agent earns exactly 1 point
- **The fingerprint test** — loads the data twice, checks the checksum is identical
- **The honest-baseline test** — runs with the project's reward off and checks the score matches
  the simulator's own move for move, proving the comparison baseline is real
- **The dynamic-range test** — fails loudly if the vulnerability list is edited into uniformity
- **The missing-data test** — confirms the system refuses to start rather than quietly training
  on incomplete data

## 5. The reward, in detail

| Event | Points | Why |
|-------|-------:|-----|
| Reaching a high-value machine | +100 | The actual objective. Deliberately dominant |
| Raising access on a machine | +0.88 to +2.50 | Scaled by severity. The research contribution |
| Privilege escalation | +2.0 | Hardest and most valuable stage |
| Scanning something new | +1.0 | Necessary, but pays only the first time |
| Breaking in | +0.5 | Small; the severity term carries the signal |
| A failed action | −5.0 | Discourages blind guessing across 120 moves |
| Data exfiltration | +1.5 | **Never triggers** — see below |

> ### Raise this with your supervisor
> The agreed reward includes **+1.5 for data exfiltration, but the simulator has no exfiltration
> action** — only scanning, breaking in, and escalating privileges. The entry is implemented and
> reported with a count of zero rather than quietly reassigned. It needs a decision: drop it, or
> redefine it — noting that "gaining full control of a high-value machine" already pays +100, so
> redefining it that way would count the same event twice.

**Why the severity reward is deliberately small.** It tops out at 2.5 while the objective pays
100. That ratio is enforced, not guessed: before training, the system calculates the maximum
bonus obtainable on that network and refuses to start unless it is below half the objective's
value. Raise the weighting too far and training stops with an explanation, rather than silently
producing an agent that learned to farm points.

## 6. What gets stored

| Table | Contains |
|-------|----------|
| `experiments` | One row per run: which reward, plus fingerprints of network settings and vulnerability data — the proof both arms were comparable |
| `episodes` | One row per attempt: length, success, machines compromised, **both** reward totals |
| `steps` | One row per move: action, machine, success, vulnerability, points — the raw material for reconstructing an attack path |

**The subtle but important one.** Every episode stores *two* reward totals: the one the agent was
trained on, and the simulator's own untouched score. The comparison must use the second. The two
agents optimise different things, so comparing their own scores would be like comparing seconds
against metres — the shaped agent would "win" automatically, on its own ruler.

## 7. User manual

Everything runs in a container, so the host machine's setup does not matter.

### First-time setup

```bash
cp .env.example .env    # add your NVD API key (never committed)
make build              # build the image — a few minutes first time
make db-up              # start the database
make test               # prove it works: all 156 tests
```

### Seeing it run

```bash
make rollout            # random agent — the baseline to beat
make train              # train the severity-rewarded agent (~70 s)
make train-sparse       # train the plain-reward comparison agent
```

### A full experiment run

```bash
python -m rlredteam.train --seed 42 --timesteps 200000 \
    --reward-config configs/shaped.yaml --postgres --log-steps

python scripts/run_ablation.py    # check arms are comparable before spending compute
```

### Where results go

| File | Contains |
|------|----------|
| `runs/<name>/config.snapshot.json` | Every setting and both fingerprints — how you prove what produced a result |
| `runs/<name>/episodes.csv` | One row per attempt; your learning curve |
| `runs/<name>/summary.json` | Success rate, average speed, average severity exploited |
| `runs/<name>/model.zip` | The trained agent. **Never committed** — dual-use gating |

### Refreshing the vulnerability data

```bash
python tools/fetch_nvd.py --fetch     # uses the internet; run by hand
make catalogue                        # rebuild the frozen database
make manifest                         # recompute the fingerprint
python tools/fetch_nvd.py --verify    # audit stored data against live NVD
```

## 8. Questions you'll be asked

**"Why not just use the raw CVSS score?"**
Because it would not be detectable. Remotely exploitable vulnerabilities cluster between 7.8 and
10.0, giving only ~1.4× spread — smaller than the run-to-run variation of the algorithm. The
curve widens it to 2.84×. It was fixed in advance from the *distribution of the data*, not tuned
after seeing results, and that distinction is what keeps it honest.

**"Isn't the result obvious? Reward severity, get severity."**
Partly yes — and saying so first is the strongest position. The interesting question is not
*whether* the agent chases severe vulnerabilities but **what it costs**: does steering it toward
severity make it slower or less reliable at the actual objective? That trade-off is a real
finding; the direction of the effect alone is not.

**"How do you know the two agents are comparable?"**
Both fingerprints — network settings and vulnerability data — are recorded with every run and
checked before training starts. A script refuses to proceed if the configurations differ in
anything except the reward.

**"Why generate networks instead of using the standard benchmark?"**
Because the standard benchmark cannot answer the question. Testing showed 7 of its 8 machines
admit only one attack method, so the agent never chooses between severities and the variable
disappears. Found by measurement, not assumption.

**"Is it reproducible if the networks are random?"**
Yes — "random" means generated from a seed. The same seed always builds the same network and
assigns the same vulnerabilities. A result is fully reconstructable from a settings fingerprint
plus a seed number, both stored with every run.

## 9. Honest limitations

1. **The exfiltration reward never fires.** The simulator has no such action. Reported as zero
   rather than quietly reassigned. Needs a decision.
2. **Vulnerability-to-service pairing is synthetic.** Severity scores are real and NVD-sourced,
   but which vulnerability lands on which generated service is a seeded draw, not a genuine
   correspondence.
3. **Ten runs is a small sample.** With the statistical correction applied, only large effects
   are reliably detectable. Effect sizes and confidence intervals should lead the reporting, not
   p-values — otherwise a sample-size limitation reads as a failed experiment.
4. **Success rate may not separate the two agents.** Even a random agent reaches the target on
   this network size. Speed and average severity are the discriminating metrics. A harder network
   may be needed.
5. **The anti-cheating rule changes the reward's character.** Because a bonus pays only the first
   time, the reward depends on what already happened in the episode, not only the current move.
